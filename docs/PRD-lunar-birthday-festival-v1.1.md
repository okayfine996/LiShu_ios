> **关联文档**: [PRD-v1.1.md](../PRD-v1.1.md) — 功能一「农历支持与智能节日提醒」

## 1. 文档目的与范围

本文档在总 PRD 的场景描述基础上，补充**数据模型、历法规则、通知调度、首页卡片、与现有代码的衔接点及边界情况**，供产品与研发对齐实现细节。

**范围内**

- 联系人农历/公历生日录入与展示  
- 农历生日本地推送（与现有公历生日提醒体系一致地扩展）  
- 内置传统节日的首页卡片与节日前提醒（亲密圈层联系人）  
- **用户自定义节日**：增删改、与内置节日合并排序展示、同一套「节日关系 R1」与提醒逻辑（见 §6.3、§4.3）  
- 与 v1.1 Pro 分层策略一致的能力划分（若与「不区分会员」的 UI 定稿冲突，以**实现时主 PRD** 为准）  

**范围外（本版不做或另文说明）**

- 农历闰月生日（见 §8.1 决策建议）  
- 服务端计算或跨设备日历同步以外的「云端农历服务」  
- **自定义节日的闰月**（农历重复类型首版不支持闰月，与联系人农历生日一致）

## 2. 术语与定义

| 术语 | 说明 |
|------|------|
| 农历月 | 正月～腊月，共 12 个常规范畴；用户选择器不区分闰月时，产品层称「农历月份」 |
| 农历日 | 初一～三十；大月 30 天、小月 29 天，由历法库按**目标年份**校验 |
| 公历生日 | 现有 `Contact.birthday` 语义：用户选择的公历 `Date`，用于展示与公历提醒 |
| 农历生日 | 用户选择的「农历月 + 农历日」；持久化建议存**农历月日整数编码** + 展示用字符串，触发提醒需换算为**当年公历日期** |
| 亲密圈层 | 与产品一致：`circle == 1`（家人）或 `circle == 2`（亲属），与 PRD「家人、亲属」对应 |
| 传统节日 | 内置固定列表，每年由农历规则映射到公历日期（见 §5） |
| 自定义节日 | 用户自建条目，重复规则见 §6.3；与内置共用首页、R1、节日管理列表 |

## 3. 用户故事（继承总 PRD）

- 作为用户，我希望为联系人设置农历生日，避免公历农历不一致导致漏祝福。  
- 作为用户，我希望在传统节日前收到提醒，并知道该问候哪些亲密亲友。  
- 作为用户，我希望在首页看到即将到来的传统节日，便于提前准备。

## 4. 场景级详细说明

### 4.1 场景 A：设置农历生日

**入口**  
添加/编辑联系人页 — 「生日」区域（与现有 `hasBirthday` + 日期选择并列演进）。

**交互**

1. **模式切换**  
   - 控件：`SegmentedControl` 或等价组件，选项：**公历** | **农历**。  
   - 默认：与当前产品一致 — 未开启生日时无模式；开启后默认 **公历**（兼容老用户数据：仅有 `birthday` 时视为公历）。

2. **公历模式**  
   - 行为与现版一致：选择公历月日（及可选年份，若产品保留「年份可选」策略则延续）。  
   - 持久化：`Contact.birthday` 存所选公历日期（语义不变）。

3. **农历模式**  
   - **月份**：正月、二月、…、腊月（本地化字符串，见 §9）。  
   - **日期**：初一～三十；**根据历法库**，在「当前预览年」或「用户选定参考年」下禁用无效日（如某月只有 29 天则不可选三十）。  
   - 持久化：见 §6.1（建议新增字段，**不**把农历强行塞进 `birthday` 的月日以免与公历混淆）。

4. **同时持有公历与农历**  
   - 当用户同时填写公历生日与农历生日时：  
     - 详情页 **两行展示**：例如「公历：1990年3月15日」「农历：八月十五」。  
     - 设置页需明确两项独立开关或「农历生日」子区块，避免误触清空。

5. **校验**  
   - 姓名等现有校验不变。  
   - 若仅开启农历、未选完整月日，保存按钮禁用或报错提示（本地化 key 见 §9）。

**联系人详情展示**

- 公历：`YYYY年M月d日`（沿用现有 `formatDate` 规则）。  
- 农历：`农历{月份名}{日期名}`，例：`农历八月十五`（月份、日期用语全部走本地化）。  
- 仅农历：只显示农历行；仅公历：只显示公历行；两者皆有：两行（顺序建议：农历在上或按产品偏好统一，需全应用一致）。

### 4.2 场景 B：农历生日提醒

**触发时刻**  
农历生日对应的**当年公历日**的 **09:00**（与总 PRD 一致；若公历生日提醒已用其他时刻，以**设置项统一**为准，避免一天多条不同时间）。

**文案（示例，正式用 String Catalog）**

- 标题：可与公历区分或统一品类，例如「生日提醒」。  
- 正文：`今天是{姓名}的农历生日（{八月十五}），别忘了送上祝福` — `{八月十五}` 为农历月日展示片段，与详情页一致。

**调度逻辑**

1. 自用户设置的农历月日，用 **Chinese lunisolar calendar**（`Calendar.Identifier.chinese` 或经评审的第三方库）计算 **下一年** 该农历日期对应的公历 `Date`（按用户时区 `Calendar.current.timeZone`）。  
2. 使用 `UNCalendarNotificationTrigger` 在当年该公历日的 9:00 触发 **一次**。  
3. 通知送达后（或 App 下次前台激活时），为该联系人 **重新调度下一年的农历生日通知**（因农历对应公历每年变动）。  
4. 与现有 `NotificationManager.scheduleBirthdayReminder` 的关系：  
   - 公历生日：仍可按月日每年重复（现有逻辑）。  
   - 农历生日：**独立** `identifier`（例如 `lunar-birthday-{stableID}`），避免与公历冲突。  
5. 若同一联系人同时有公历与农历生日且经换算落在同一天，**合并为一条通知**（文案可优先农历或并列说明），避免重复打扰。

**开关**

- 沿用「生日提醒」总开关；若需细分，可增加「农历生日提醒」子开关（产品决策：默认与「生日提醒」同开，减少设置项）。

**Pro**

- 与主 PRD 一致：**农历生日推送与公历生日推送同属「生日类推送」** 时，免费用户策略需与 `settings` / 会员表一致（主 PRD：农历设置与显示免费；若推送区分 Pro，则仅 Pro 推送 — 以主 PRD §Pro 分层为准）。

### 4.3 场景 C：传统节日提醒与首页卡片

**内置节日列表（固定）**

春节、元宵节、端午节、七夕、中秋节、重阳节、除夕  

每条需配置：

- 稳定 `id`（用于排序、埋点、深度链接）  
- 展示名称（本地化）  
- **农历规则**：月日锚点（除夕为腊月最后一天，需按年计算）  
- 默认建议关联的 **事件类型**：`EventType.festival`（或子类型若后续扩展；首版可用 `festival` + 预填名称）

**首页卡片**

- 展示「即将到来的」**内置 + 自定义**节日，统一按**下一个公历 occurrence 距今天数**升序排序；数据源合并时须区分 `festivalKind`（内置 id / 自定义 `PersistentIdentifier`）。  
- 条数：首页仅展示前 **N** 条（与 [UI-lunar-calendar-festival-v1.1.md](./UI-lunar-calendar-festival-v1.1.md) 一致）；**不**含自定义时仍只显示内置。  
- 卡片文案示例：`中秋节 · 还有 12 天`；自定义示例：`家祭 · 还有 3 天`（名称为用户所起）。

**节日前 1 天推送（Pro）**

- 触发：节日前一日 **09:00**（或与生日提醒统一时间配置）。  
- 正文示例：`中秋节即将到来，别忘了问候张三、李四等亲友`。  
- **联系人范围**：`circle == 1 || circle == 2` 的联系人；按姓名排序，**最多显示 N 个名字**（建议 3～5），超出用「等」或「等 N 位亲友」。  
- 若无符合条件的联系人：不发送该节日的「问候名单」类通知，或改为通用文案（产品二选一，建议无亲密联系人则**不推送**，减少噪音）。

**点击卡片**

- 打开 **节日关系（R1）** 界面：问候名单、已问候状态、「问候过了，记一下」等；详见 [UI-lunar-calendar-festival-v1.1.md](./UI-lunar-calendar-festival-v1.1.md)。  
- 路由：与现有 `AppRoute` / Sheet 规范一致，不新增嵌套 `NavigationStack`。

**节日管理（全屏）**

- 展示**全部内置节日**与**全部自定义节日**；支持 **新增 / 编辑 / 删除** 自定义项；可选「节日前提醒」按条目管理（与总通知开关的关系见该文档）。  
- 入口：设置、或首页「查看全部」等；详见 [UI-festival-management-v1.1.md](./UI-festival-management-v1.1.md)。

## 5. 传统节日历法规则（产品约束）

实现侧必须用同一套农历数据源计算「今年/明年」的公历日期，并与系统 `Calendar` 时区一致。

| 节日 | 规则说明（摘要） |
|------|------------------|
| 春节 | 农历正月初一 |
| 元宵节 | 正月十五 |
| 端午节 | 五月初五 |
| 七夕 | 七月初七 |
| 中秋节 | 八月十五 |
| 重阳节 | 九月初九 |
| 除夕 | 农历年最后一天（腊月廿九或三十，依年份而定） |

**排序与「下一个」**  
以「从今天起算的下一个 occurrence」为准；若今年该节日已过，则取下一年。

## 6. 数据模型建议（SwiftData）

### 6.1 Contact 扩展（建议）

| 字段 | 类型 | 说明 |
|------|------|------|
| `birthday` | `Date?` | 保留：公历生日 |
| `lunarBirthdayMonth` | `Int?` | 可选：农历月 1～12（正月=1 … 腊月=12） |
| `lunarBirthdayDay` | `Int?` | 可选：农历日 1～30 |

**语义**

- 仅公历：`birthday != nil`，农历字段为空。  
- 仅农历：公历可为空或仅存「占位」— **推荐** `birthday == nil`，农历月日非空。  
- 两者皆有：三个字段均有值。  

**迁移**  
老数据仅 `birthday`：视为公历；农历字段默认 `nil`。

### 6.2 索引与查询

- 首页节日卡片：内置条目由静态表 + 历法计算；自定义条目由 `UserFestival`（见 §6.3）取「下一次 occurrence」后**合并排序**。  
- 推送名单：`FetchDescriptor` + `#Predicate` 过滤 `circle == 1 || circle == 2`。  

### 6.3 自定义节日（SwiftData 建议）

新增 `@Model`（名称示例：`UserFestival`）：

| 字段 | 类型 | 说明 |
|------|------|------|
| `name` | `String` | 用户输入的名称（展示于首页、R1、通知文案） |
| `recurrenceRaw` | `String` | 重复类型：`annualGregorian` / `annualLunar` / `oneTime` |
| `gregorianMonth` | `Int?` | 每年公历：`1…12`（仅 `annualGregorian`） |
| `gregorianDay` | `Int?` | 每年公历：`1…31`（仅 `annualGregorian`） |
| `lunarMonth` | `Int?` | 每年农历：`1…12`（仅 `annualLunar`，规则同联系人农历月） |
| `lunarDay` | `Int?` | 每年农历：`1…30`（仅 `annualLunar`） |
| `oneTimeDate` | `Date?` | 仅一次：当日 0 点所在公历日（仅 `oneTime`） |
| `reminderEnabled` | `Bool` | 是否参与节日前提醒（与方案 B 分节日开关对齐；默认 `true`） |
| `createdAt` | `Date` | 创建时间 |
| `sortOrder` | `Int` | 可选：列表内手动排序 |

**重复语义**

- **annualGregorian**：每年同一公历月日；闰年 2 月 29 日可按平台惯例滚到 2 月 28 日或 3 月 1 日（实现定一条）。  
- **annualLunar**：每年同一农历月日；换算使用 `Calendar(identifier: .chinese)`，**不支持闰月**首版。  
- **oneTime**：仅在 `oneTimeDate` 当日及前后提醒逻辑与内置「节日前一天」一致；**过期后**（occurrence 已过）：节日管理列表可显示「已过去」或隐藏，由产品二选一；首页卡片**不再展示**已过期的一次性节日。

**删除**：用户删除 `UserFestival` 即移除提醒与列表项；**不**影响已有关联记录（若记录仅备注含节日名，不做级联）。

**与内置去重**：允许用户起名「中秋节」与内置重名；靠 `festivalKind` 区分，不强制唯一名称。

### 6.4 CSV / 导出（若联系人导出含生日）

- 增加列：`农历生日`（如 `八月十五` 或 `8-15` 规范），与 PRD 全局「兼容旧格式」原则一致：旧文件无列则按无农历处理。  
- **自定义节日导出（可选）**：独立「导出我的节日」JSON 或并入设置导出；不必塞进联系人 CSV。

## 7. 技术实现要点（研发）

1. **历法**  
   - 优先使用 `Calendar(identifier: .chinese)` 做农历↔公历换算；除夕需单独按年取「腊月最后一天」。  
   - 单元测试覆盖：已知年月的春节/中秋公历日期抽样、闰年除夕。

2. **通知**  
   - 农历生日：`removePendingNotificationRequests` + 按年调度，**identifier** 稳定可取消。  
   - 节日提醒：每节日每年一条或统一 scheduler 批量注册；注意 **通知权限** 关闭时与现有 `NotificationManager` 行为一致。

3. **后台刷新**  
   - 每年元旦或 App 启动时 **刷新** 未来 12 个月的农历生日与节日触发器，避免遗漏。

4. **设计系统**  
   - 所有新建 UI 仅用 `DesignSystem` 令牌；字符串仅 `String(localized:)` + `Localizable.xcstrings`。

## 8. 边界与异常

### 8.1 闰月生日

- **首版建议**：选择器仅支持「常规十二月」，**不支持闰月**；若用户强烈需要可列入 v1.2。  
- 若未来支持：需增加「闰月」标记及历法库对闰月日的换算。

### 8.2 农历三十

- 小月无三十：选择器动态禁用「三十」；保存时若从大年切换到小年需降级为「廿九」或提示用户（编辑场景）。

### 8.3 时区与旅行

- 提醒以设备当前时区计算；用户跨时区时以系统时区为准（与常见日历应用一致）。

### 8.4 权限

- 通知关闭：界面提示与现有设置页一致；不静默失败。

### 8.5 自定义节日条数

- 建议设 **上限**（如 20 条）防止通知与列表膨胀；触达上限时「添加」按钮禁用并提示。

## 9. 文案与本地化

- 所有用户可见字符串写入 `Localizable.xcstrings`，key 建议：`contact.birthday.mode.gregorian`、`contact.birthday.mode.lunar`、`home.festival.card.daysLeft`、`notification.lunarBirthday.body`、`notification.festival.eve.body` 等。  
- 农历月份、日期：用 `Locale`/`String(localized:)` 或资源表枚举，避免硬编码中文在代码中。

## 11. 验收标准（细化）

- [ ] 添加/编辑联系人可在公历/农历生日模式间切换，农历为正月～腊月、初一～三十（随月动态限制三十）。  
- [ ] 详情页展示与总 PRD 一致；公历+农历同时存在时两行展示。  
- [ ] 农历生日在正确公历日 9:00 触发（用户时区）；次年自动按新农历对应公历重算。  
- [ ] 公历与农历生日同一天时通知去重。  
- [ ] 首页展示未来最近的节日卡片（内置 + 自定义合并排序，条数 N）；「查看全部」含自定义。  
- [ ] 可添加、编辑、删除自定义节日；三种重复类型行为符合 §6.3。  
- [ ] 节日前推送（若主 PRD 为 Pro）正文含 `circle` 1/2 联系人姓名列表（有上限与溢出处理）。  
- [ ] 点击节日卡片进入 **节日关系 R1**（内置 / 自定义共用）。  
- [ ] 老数据迁移无破坏；关闭通知时不崩溃。  
- [ ] Light/Dark 与设计系统合规。

## 12. 依赖与顺序

- 与总 PRD「功能依赖」一致：本功能可独立开发；依赖 **通知权限、Contact 模型迁移、首页列表区域**。  
- 建议实现顺序：**数据模型 + 历法工具 → 编辑/详情 UI → 通知调度 → 首页卡片 → 节日推送**。

## 13. 开放问题（需产品拍板）

1. 公历生日是否必须保留「年份」用于年龄相关展示？农历是否同样需要存「出生农历年」用于生肖（本 PRD 未要求）。  
2. 生日提醒 9:00 是否与现有公历生日提醒时间完全一致（若现有非 9:00，是否统一调整）。  
3. 免费用户首页 3 个节日：按时间最近取 3 个，还是固定优先级（如春节永远优先展示）。  
4. 节日推送在无亲密联系人时：静默不推还是推送无名单版。  
5. 自定义节日默认上限条数（如 20）是否可调。
